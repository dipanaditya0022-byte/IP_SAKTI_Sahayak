1. Executive summary

IP-SAKTI Sahayak is a decision-support system for Ayurveda intellectual property, scientific evidence and regulatory pathways in India, the USA and Australia. It answers only from a curated document corpus, ties each claim to a source passage, checks each claim against that passage, and abstains when evidence is missing or conflicting. It does not determine patentability, approval or efficacy.

As of this report, the following are implemented and running: user and admin areas with separate sign-in, an innovation workflow (profile, classification, evidence, scientific, patents, regulatory, gaps, graph, review), a research assistant with hybrid retrieval and claim verification, an escalation workflow, reports, and an admin console for corpus, monitoring and evaluation.

Verified in this report cycle: 69 of 69 backend tests pass. The frontend type-checks and builds. All 47 page routes load without JavaScript errors for their intended role. Access-control checks return the expected 401 and 403 responses. Chat, patent search and innovation analysis return real results from the local corpus. The full evaluation suite result is in section 14.6.

2. Problem and scope

An Ayurveda product needs three answers before it reaches the market: whether it is patentable and what prior art exists, which regulator governs it and under what category, and whether the evidence supports the claims. The sources are statutes, gazette notices, patent databases and journals, often in different languages and naming the same herb differently.

The design goal is traceability and honest abstention. A fluent but unsourced answer is treated as a failure, not as a success.

Out of scope

  • Legal advice, patentability opinions, regulatory approval, or efficacy determination.
  • Access to TKDL records or other restricted traditional-knowledge databases. The system declares this limit and does not scrape them.
  • Live feeds from official sources. The corpus is a curated seed.

7. Retrieval, reranking and generation

  1. Query understanding. Language detection (English and Hindi), terminology normalisation for Ayurveda names, and intent classification.
  2. Hybrid retrieval. pgvector HNSW similarity search and PostgreSQL full-text search run together. Results are filtered by jurisdiction, document type and workspace in SQL, before reranking.
  3. Deterministic reranking. Each candidate is scored from jurisdiction match (weight 0.12), source authority (weight 0.12) and freshness (weight 0.06), plus relevance terms. There is no learned cross-encoder.
  4. Authority tiers. Tier 1 (official law or regulator) = 1.0, tier 2 = 0.85, tier 3 = 0.7, tier 4 = 0.5, tier 5 (user-provided, unverified) = 0.3.
  5. Freshness labels. Current = 1.0, Recently checked = 0.85, Potentially stale = 0.5, Unknown = 0.4, Superseded = 0.1.
  6. Generation. The selected LLM provider writes an answer from the retrieved passages. In mock mode, the answer quotes retrieved passages directly. Retrieved text is treated as data, not as instructions.

Embeddings: the default provider is hashing (1024 dimensions, in-process, no network). The evaluation run in section 14.6 reports the embedding provider as hashing-ngram. OpenAI and bge-m3 are available by configuration. Hashing captures shared words, not synonyms, so synonym recall is weaker than with a semantic model.

8. Citation verification and abstention

Each claim in an answer is checked against the cited passage. Verification verdicts are SUPPORTED, PARTIALLY_SUPPORTED, UNSUPPORTED and CONTRADICTED. The evidence status shown with an answer can also be CONFLICTING or INSUFFICIENT.

A confidence score is shown with a signal breakdown: claim verification score, share of fully supported claims, source authority, jurisdiction match and other signals. The score is a heuristic, and the response marks it as such.

The assistant abstains when: the jurisdiction is not supported (rejected at the schema level, see section 9), clarification is needed, the evidence is insufficient, or the query looks like a prompt-injection attempt.

9. Jurisdiction handling

  • Supported jurisdictions are IN, US and AU. Request schemas reject any other value with HTTP 422 (verified with JP).
  • Document jurisdictions also allow INTERNATIONAL. Retrieval always includes international documents alongside the selected jurisdiction.
  • An innovation's target markets limit its patent matching. An EP-jurisdiction patent is therefore never matched to an innovation.
  • Jurisdiction is chosen once on the landing page and kept in the browser. The dashboard, assistant and research pages read the same value.
  • Admin analytics group RAG and citation events by jurisdiction. Events without a jurisdiction (for example, scientific queries) are shown under ?, not hidden.

10. Security and access control

Scope separationThe user dependency accepts only user-scoped tokens. The admin dependency accepts only admin-scoped tokens and re-checks role=ADMIN on every request.
Cross-scope responsesA user session on an admin endpoint returns 403 (ADMIN_ACCESS_DENIED). An admin session on a user endpoint returns 401.
CSRFCookie-authenticated writes must send X-Requested-With: ipsakti. Requests without it return 403 CSRF_CHECK_FAILED.
Frontend route guardsfrontend/middleware.ts redirects /app/* without a user cookie to /login, and /admin/* without an admin cookie to /admin/login. Middleware checks cookie presence only. The backend validates the token on every API call.
Admin discoverabilityThe admin sign-in page is not linked from any public page or from the user app. It carries only the label "Administrator access".
AuditKey actions are written to the audit log. IP addresses are stored as keyed SHA-256 hashes (keyed with the session secret), not in raw form.
Workspace isolationInnovations, conversations, documents, reports and escalations are filtered by workspace membership on every query.
Development defaults. JWT_SECRET defaults to a development value. The config raises an error in production if it is not set. Demo accounts use a shared, seeded password for local use only.

14.6.3 Latency (this run)

p50 54.3 s, p95 86.2 s, mean 48.2 s per question, on a local machine running a 7B model on CPU. These numbers are much higher than the 34 s p50 in section 14.5, which came from three queries. Production latency depends on hardware and the chosen model.

14.6.4 Innovation classification (8 cases, 13 labels across 3 jurisdictions)

Agreement with the expected label: 13 of 13 (100%).

Read this with care. The expected labels were assigned by the project team against the seeded pathway definitions. The classifier uses the same definitions. So 100% agreement shows that the logic is consistent with those definitions, not that it matches expert regulatory judgement. The labels need review by a qualified regulatory expert before this number is used as evidence of accuracy.

14.6.5 What these results do and do not show

  • They show that, on this seed corpus and these 20 questions, retrieval finds the expected sources, abstention and jurisdiction rules behave as designed, and citation checks catch unsupported claims at a low rate.
  • They do not show accuracy on real documents. The corpus is a seed of 40 documents, and 9 of them are fictional (section 12).
  • The question set is small (20) and written by the project team, so it can favour the system's own design.
  • The harness counts 20 of 20 questions as passed under its own rules. This is not an independent expert review.

15. Known limitations

  • The corpus is a seed of 40 documents. Statute summaries need checking against official texts. Patents are fictional.
  • Hashing embeddings do not match synonyms well. A semantic embedding model is not connected in the current setup. Synonym questions passed, but two of them were only partially supported.
  • Classification labels were written by the project team and need expert review (section 14.6.4).
  • Latency depends on the local model. The evaluation run shows p50 of 54 s; an earlier sample of three queries showed 34 s.
  • Rate limiting runs in-process. Background jobs run inside the web worker. A larger deployment needs Redis and a separate worker.
  • The public demo link is temporary and changes on restart. Production hosting is not set up.
  • No formal WCAG 2.0 AA audit has been done.
  • Admin access is held by the project lead for now. Further admin accounts are not yet needed.

16. Next steps

  1. Add further administrator accounts only when the team needs them, using the create-admin command.
  2. Decide production hosting and a real contact address.
  3. Connect a semantic embedding model and an LLM key, then re-run the evaluation suite.
  4. Verify the corpus against official texts and move reviewed documents out of SEED_SUMMARY.
  5. Run a formal accessibility audit.
